# Executive Summary

The UUID Strategy defines how unique identifiers are generated and managed across all EHMS microservices.

Each business entity receives a globally unique identifier (UUID), enabling distributed data creation without collisions and simplifying data synchronization between services.

Business identifiers (such as UHID and Invoice Number) are maintained separately from internal UUIDs.

---

# 2. Why UUID?

UUIDs provide:

- Global uniqueness
- Distributed generation
- No central sequence dependency
- Better support for microservices
- Easier data migration
- Safer data synchronization

---

# 3. Identifier Types

EHMS uses two types of identifiers.

## Internal Identifier

Used by the database.

Example

```
id

UUID
```

---

## Business Identifier

Visible to users.

Examples

```
UHID

EMPLOYEE_CODE

DOCTOR_CODE

APPOINTMENT_NUMBER

INVOICE_NUMBER
```

Business identifiers are human-readable and may follow organizational formats.

---

# 4. UUID Standard

Preferred:

```
UUID Version 7
```

Fallback:

```
UUID Version 4
```

The choice depends on PostgreSQL and Prisma support at implementation time.

# 6. Prisma Example

```prisma
model Patient {

  id String @id @default(uuid()) @db.Uuid

  uhid String @unique

  firstName String

  lastName String

  createdAt DateTime @default(now())

  updatedAt DateTime @updatedAt

  @@map("patients")

}
```

---

# 7. Foreign Keys

Every relationship uses UUID.

Example

```text
appointment.patient_id

↓

patients.id
```

Cross-service references store only the UUID of the external entity and resolve additional data through APIs or events.

---

# 8. Business Identifier Rules

Business IDs must be:

- Unique
- Human-readable
- Immutable
- Searchable

Examples

```
UHID

EHMS-PT-000001

Doctor

DOC-000145

Invoice

INV-2026-000125
```

---

# 9. Generation Strategy

UUIDs

Generated automatically.

Business IDs

Generated by the owning service according to business rules.

Example

Patient Service generates

```
EHMS-PT-000001
```

Billing Service generates

```
INV-2026-000001
```

---

# 10. Cross-Service References

Example

Appointment Service stores

```text
patient_id

doctor_id
```

Additional patient or doctor information is retrieved through service APIs or subscribed events.

---

# 11. Security

UUIDs reduce predictability compared to sequential integers.

Business identifiers should not expose sensitive information.

---

# 12. Performance Considerations

To maintain performance:

- Index UUID primary keys.
- Index business identifiers.
- Use efficient UUID generation.
- Monitor index growth.

---

# 13. Migration Strategy

Existing integer keys (if any) should be migrated carefully to UUIDs through planned migrations.

New EHMS services use UUIDs from the beginning.

---

# 14. Architecture Decisions

| Decision | Reason |
|----------|--------|
| UUID primary keys | Global uniqueness |
| Business identifiers | Human-friendly |
| UUID foreign keys | Consistency |
| Separate business IDs | Better usability |
| UUID generation in application/database | Distributed architecture |

---

# 15. Risks & Mitigation

| Risk | Mitigation |
|------|------------|
| Larger index size | Proper indexing |
| Human readability | Business identifiers |
| UUID misuse | Standard generation policy |
| Duplicate business IDs | Unique constraints |

# 18. Conclusion

The UUID Strategy establishes a consistent identification mechanism across EHMS by combining globally unique internal identifiers with human-readable business identifiers. This approach supports distributed microservices, improves scalability, and maintains usability for hospital staff.
